## 2. What v0.3.0 must deliver

v0.3.0 has three pillars, ranked by user-visible value:

1. **Single-binary Windows distribution (Phase 4 retry).** The
   audit's U2 / U3 / U4 / U6 / C2 findings (install-path cluster)
   are still open until the bundle ships. The bundle infra
   (`omniscribe_server.spec`, `scripts/build_windows.py`,
   `scripts/run_server.py`, `hooks/hook-anyio.py`) is in tree;
   the missing piece is the bundler decision.
2. **U12 — in-UI "try with sample PDF" affordance.** End-user
   audit U12: a new user has no easy way to confirm the install
   works without finding their own PDF. **Approved: Option (b) —
   FastAPI `/sample-pdf/{name}` route** that the Flutter client
   calls. Backend ~2 hours + Flutter ~2 hours. Backend serves the
   canonical PDF from `tests/fixtures/pdfs/`; Flutter adds a "Try
   sample" button that calls the route.
3. **Long-tail backlog from the 2026-09-04 audit.** The Phase 6
   opportunistic picks are closed, including D9 and Q9 (see §1).
   The remaining items are the multi-day ones:
   - **Q11** — chaos / fault-injection tests (multi-day).
   - **Q12** — Flutter `integration_test/` against a real
     running server (multi-day; Flutter-side).
   - **Q13** — balance Flutter widget test coverage
     (multi-day; Flutter-side).
   - **Redis state backend** — `OMNISCRIBE_STATE_BACKEND=redis`
     currently crashes at plugin apply. Multi-day work;
     defer to v0.3.1 unless a Profile 4 (multi-worker LAN)
     deployment is in flight.
   - **Model pre-flight route** — `ensure_model_loaded()` exists
     as private; the public API route is unbuilt. Out of scope
     for v0.3.0 (no user call).

## 3. The bundle decision (CONFIRMED: Option (a))

The PyInstaller + `anyio` static-analysis interaction is documented
in [`docs/deployment/windows-bundle.md`](../deployment/windows-bundle.md)
§"Known build issue". Three options on the table:

| Option | Description | Risk | Time | v0.3.0 impact |
|---|---|---|---|---|
| **(a) Wait for upstream** ✅ | Track [pyinstaller/pyinstaller](https://github.com/pyinstaller/pyinstaller/issues). If the `anyio` analyzer fix lands in a release we can pull, we ship Option A as written. | Low (no engineering) but unbounded (could be weeks or months). | 0 engineering now | Unblocks the bundle "for free" if upstream moves. |
| (b) Switch to Nuitka | Replace PyInstaller with [Nuitka](https://nuitka.net/). Nuitka has had fewer `anyio` problems historically. | Medium — unknown how the rest of the dep tree (torch, surya-ocr, pymupdf) behaves under Nuitka. The torch-bundled DLLs are known to need special handling. | 2-3 days of bundler porting + smoke test gate | Bundle ships, but the build script changes. |
| (c) Accept source install as the long-term path | Document the 12-step source install as the supported end-user path. The bundle infra stays in tree for the next maintainer but the v0.3.0 release notes say "no single binary in v0.3.0". | None (decision-only) | 0 engineering | Bundle infra rots; the next maintainer picks (a) or (b) for v0.4.0. |

**Decision (2026-09-06): Option (a) with a v0.3.0 cap.**

**Sprint 1 plan (1-2 days):**
- Write a minimal reproducer (strip the current `omniscribe_server.spec`
  down to the smallest spec that still triggers the `import anyio.abc`
  static-analysis failure).
- File a new upstream issue at pyinstaller/pyinstaller with the
  reproducer + a link to the existing anyio-related issues.
- Monitor for a fix in a release. Set a v0.3.0 feature-freeze
  deadline for the decision point.

**Sprint 2 plan:**
- If upstream has moved → ship Option A bundle. Validate the
  `scripts/build_windows.py --smoke` gate
  (`/api/health -> 200`).
- If upstream hasn't moved by the v0.3.0 feature freeze → fall
  back to (c). Update the v0.3.0 release notes to "single binary
  deferred to v0.4+", keep the bundle infra in tree.

## 4. U12 — "try with sample PDF" (CONFIRMED: Option (b))

End-user audit U12: a new user has no easy way to confirm the
install works without finding their own PDF.

**Decision (2026-09-06): Option (b) — FastAPI `/sample-pdf/{name}` route.**

The route serves a canonical PDF from `tests/fixtures/pdfs/`
(e.g. `multi_page_layout.pdf`) on the same auth path as a normal
job submission, so the user sees a real round trip (upload →
process → download) without leaving the UI. The Flutter Workstation
gets a "Try sample PDF" button that calls the route.

Sprint 3 scope:
- **Backend** (`src/omniscribe/plugins/sample_pdfs/` or similar):
  read-only route, canonical filenames, stream the PDF bytes with
  `Content-Disposition: attachment; filename="..."`, route through
  the existing bearer auth + upload size middleware (no new
  security surface).
- **Flutter** (`client/`): a "Try sample PDF" button on the
  Workstation screen. Calls the route, lands the result in the
  normal job pipeline.

Rough effort: backend ~2 hours, Flutter ~2 hours. Total ~half a
sprint.
